01

大流程：计算链不变，通信两端去重

下文“基线”指旧版未去重的 shared + Prefetch 通路。对照保持四卡、共享专家、量化类型和计算尺寸一致。

BASELINE · 按专家处理

同一目标卡命中几个专家，就有几份通信

准备输入、交换 compact 路由源卡量化输入；目标卡知道每个专家要哪些 token

本卡多个专家共享一次输入传输、一次结果回传

基线

使用 compact topkIndex 路由列表，按专家和来源卡组织；无需建立跨专家的 token 成员表。

PR 的变化

保持路由列表格式，接收端 AIV1 新增 prepass，把同一来源 token 在本卡的多处行位置关联起来，写入 rowDesc。

共享专家不进入这张去重表。 这里的去重发生在路由专家之间。每卡的共享专家仍计算本卡全部 8192 个 token，最后由 Unpermute 合入输出。

上面按完整 token 向量统计逻辑份数，输入仅计 H 个 FP8 元素，不含 scale、权重尾段和控制信息。基线每份输出还会拆成多个 N 切片请求；本卡专家输入仍展开为 3 行，PR 没有把它压缩成共享一行。

FIRST 的“第一”

描述表成员按本卡专家顺序排列。最前面的成员负责拉取与扇出，不是运行时谁先抢到谁负责。

LAST 的“最后”

指该 token 在这张卡上命中的最后一个专家，不是整张卡的最后一个专家，也不是整个模型最后一层。

只命中一个专家

走 PLAIN 单成员路径，照常拉取和回传，不做多专家求和。每卡有 64 个专家，不意味着每个 token 都有本卡重复。

03

Prepass：先扫描路由收集成员，再按行写出描述表

下面按实际执行顺序展开。接收端 AIV1 完成这些操作；此时只读写路由和描述信息，token 的输入向量由后面的 Dispatch 搬运。

专家的 token 列表 → 按 token 编号追加成员 → 得到每个 token 的完整组 → 给组内每一行写描述符。
  1. 先拿到列表与计数，确定每一行将放在哪里。

    路由交换完成后，本卡已有 [本卡专家][来源 rank] 对应的 compact 列表。每项保存 topkIndex = tokenId × topK + k，列表按此值升序排列；k 是该 token 在源卡 top-k 中的位置。累计计数给出每份列表的起始行号 rowBase。

    接收行号 row = 前面所有列表的累计行数 + 本列表内的位置
             = rowBase + 列表分段起点 + 段内位置

    这里的行号是本卡展开输入/输出区的逻辑行位置。计数已确定位置，输入向量还没有搬过来也能建表；不同矩阵再按各自列宽把行号换成地址。

  2. 把“来源 rank × token 编号区间”分给 AIV1。

    以 BS8192、EP4、top-k6 为例，每来源卡的编号区间切为 [0,512)、[512,1024)……共16段，形成 4 × 16 = 64个工作项。编号为 srcRank × 16 + 段号，28个 AIV1 按核号起步、每次加28领取：AIV1-00做0/28/56，AIV1-01做1/29/57，依此类推。同一来源 token 的所有本卡专家命中，始终归同一个工作项收集。

    512是这组参数算出的段宽。其他 BS/top-k 会结合 UB 容量和负载目标调整，编号段也不是 GMM 的 wave 或 mgroup。

  3. 为这一段准备能直接索引的 UB 临时表。

    以来源 Rank1 的 [0,512) 为例，先初始化512个 token 的计数与最小 k 状态。每个 token 还预留最多 top-k 个成员的位置。读取到 token42 时直接访问槽 42 − 0 = 42，不必先搜索“token42在哪”。成员按 (row, topkIndex, ready偏移) 三元组追加。

    没有命中本卡的 token 也有临时索引槽，但计数保持0，之后不会生成描述符。成员区只写有效项，无需整块清零；工作项结束后，这块 UB 可复用于下一段。

  4. 按专家顺序扫描，把命中的条目追加到对应 token 的槽。

    从 E0 到 E63，逐一读取该来源 rank的列表。每次通过 MTE2 最多搬1024个 int32条目（4 KiB）到 UB，再在 UB 中逐项判断：低于本编号段则跳过，达到上界则结束本列表扫描；段内条目用除法、取模还原 tokenId 与 k，算出 row，然后追加成员、增加计数并更新最小 k。

    同时根据该行在专家内的位置，预先算出它属于哪个256行块及对应的供数 ready 偏移。以后 Dispatch 扇出时就能直接发布标记。

  5. 全部专家扫描结束后，遍历临时表，给每个接收行写 rowDesc。

    无成员就跳过；正常未截断时，只有一个成员就写 PLAIN，多成员则按已收集的专家顺序标 FIRST、LAST。每个成员行都写一份完整成员列表和相同的最小 k，只有 FIRST/LAST 标记随当前行变化。因此后续读取任意一个成员行的描述符，都能知道同组的所有位置。

  6. 确认本工作项的描述符全部写完，再发布 ready。

    描述符先在两个 UB 半区中交替拼装，再用 MTE3 写到 GM；复用半区前等上一笔写完成。工作项末尾排空两半区的写操作，才发布该编号段的 ready。所有本核工作项完成后，再增加本核 done 计数；本核不等其他 AIV1 一起结束。Dispatch 按需等对应编号段，Combine 另检查全体建表 done。

三元组中的 fE0/fE3/fE7 代指预先算出的 ready 偏移。255、253、257分别来自不同专家的列表，跨列表不要求递增。扫描顺序决定 FIRST/LAST；返回槽取最小 k，因此本例 FIRST 在 E0，最小 k=1 却来自 E3，两者不是同一个概念。

后面的编号段，仍需读取列表前面的部分。

例如处理 [512,1024) 时，各专家列表依然从第0项开始分段搬入 UB，没有保存上一段的扫描游标。若一段的末项仍小于下界，可以整段跳过逐项判断，但这段数据已经通过 MTE2 读过了；跨越下界的段还要逐项跳过前面的条目。遇到上界即可结束当前列表，后续部分不用读。

所以一次扫描服务一整段 token，而不是每个 token 分别扫全部专家；不同编号段之间却会重复读取列表前缀。扫描、UB 归组、复制完整描述符，都是 prepass 的实际成本。

容量截断的边界路径另保留“全量出现数”和“有效成员数”，最小 k 取全量出现范围，保证与源卡选择的返回槽一致；上面的三成员示例按未截断情况讲解。

04

Dispatch：省跨卡重复拉取，仍保留专家展开输入

“拉一次”与“只存一份”是两个不同目标；这个 PR 实现了前者。

一次 FIRST 的实际动作

  1. 等待本批需要的 prepass 编号段 ready。
  2. 读取当前行的 rowDesc；普通行正常处理，组内非 FIRST 行跳过拉取。
  3. FIRST 从来源卡读取一份量化 token（含需要的附属信息）。
  4. 从 UB 写入所有成员的专家输入位置；这些位置可能属于后续 wave。
  5. 按成员更新路由信息并发布对应供数标记，GMM1 按原依赖消费。

为什么还要多份输入？

各专家的 GMM1 仍读取自己的展开矩阵，矩阵行连续、调度方式不变。PR 只把多次跨卡读换成一次读与多次卡内写。

源 token ── 一次拉取 ──→ UB
                           ├→ E0 输入行
                           ├→ E3 输入行
                           └→ E7 输入行

“GMM1 直接读共享行、免扇出物化”是另一个潜在优化，当前 PR 未实现；它需要处理间接索引与不连续的 A 矩阵加载。

谁负责搬运？ 这里的去重 Dispatch 仍在 AIV1 路径中。没有把重复 token 的拉取单独交给 AIV0。来源就是本卡时，同样走本地供数逻辑；这不产生跨卡流量。
05

Combine：等 LAST 的专家完成，再汇总整行

改变了就绪粒度、累加位置和发送粒度。它并非只把某次 Add 的长度改大。

维度旧版未去重基线PR 去重 Combine
何时可处理按相应 GMM2 tile 输出就绪推进等当前专家各 AIC 的 GMM2 全部完成；跨 wave 的专家要等最后一段
谁的结果发送每个专家的输出分别发送PLAIN 正常发；重复组非 LAST 跳过；LAST 合并全部成员
求和在哪里源卡 Unpermute 汇总专家贡献专家所在目标卡先用 UB 的 FP32 累加；源卡再合并各 rank 代表结果

发出的数据一个 token 的一个 N 切片；BF16 256 列为 512 B整个 H 行转换为 BF16 后发送；当前每行 8 KiB

06

哪些调度沿用基线，哪些内存是新增的？

减少通信不等于减少计算或立即缩小所有中间缓冲区。

沿用：专家顺序与 wave

wave 按 mgroup 的任务及 N 切片推进，可跨专家边界；一个专家行数很多时，也可跨多个 wave。仍先推进前面的专家，再处理后面的专家。

初次 Dispatch 准备 W0/W1，随后滚动提前供数。并没有变成“做完某批 token 的所有专家，再处理下一批 token”。

沿用：GMM2 / Combine 滞后一拍

每卡 token 数 ≥4096 时启用。当前 8192 命中此门槛：GMM1(W1) 后，再推进 GMM2(W0) 及其 Combine。

这在旧基线 74d478872 中已经存在，不是 PR11646 新增。 PR 把去重 Combine 接到既有调度位置，并补充整专家完成标记。

为什么不能直接改成两个 wave 的缓冲？ FIRST 会写未来专家的输入，LAST 会回读较早专家的输出，跨 wave 的生命周期被拉长。若缩成环形缓冲，需要消费完成确认、释放规则和反压；当前 PR 没有实现。它也没有额外建立全量重复 token 输入 cache 或 GM FP32 部分和。
开关与支持范围：不是所有配置都自动开启

comm_alg="dedup" 双开；dedup_dispatch 和 dedup_combine 分别单开，空字符串默认关闭。实际 tiling 还经过收益门。

host 按均匀路由模型估计收益，不读取本轮真实重复率。本例公式估计 86.78125 MiB，超过大 BS 的 60 MiB 门槛。Combine 位还受 H≤10240 等约束，仅适用于非量化 Combine。PR 接入 arch35 MTE 的 A8W8/A8W4/A4W4；本次只验证 MXFP8 E5M2 + BF16 回传这一条，不把它称为 INT8。
