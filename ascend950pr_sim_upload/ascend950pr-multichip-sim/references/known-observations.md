# helper 的两个现象：等待区间变短，以及执行记录插入冲突

这份说明讨论的是**采集数据怎样被整理成流水记录**。我们用 `npusim record -c` 跑了 950PR 双卡 Dispatch 和 MegaMoE，两个非平凡用例的实际输出都通过了数值核对。因此，目前没有证据表明这两个现象导致了算子算错；需要确认的是报告中的时间信息是否符合工具的设计，以及有没有用错数据入口。

环境为 CANN `9.2.0-weekly.20260902.01`。下面的例子都取自成功运行后保留的原始文件，没有先修改数据库再观察结果。完整工具版本见 PROVENANCE.json（配套归档文件）。

## 先说明数据从哪里来

同一次仿真里，我们有两种可以相互核对的数据：

1. **模型的原始指令记录**：双卡分别保存在 `chip0_instr.bin` 和 `chip1_instr.bin`。里面记录指令事件发生的时刻，以及核号、指令编号、指令地址、名称和参数。对下面选出的指令，可以找到一条 popped 记录和一条完成记录。
2. **helper 整理后的数据库**：分别是 `chip0.db` 和 `chip1.db`。其中 `ExecutedInstructions` 表把事件整理成一条条执行记录，包含开始时间、结束时间和执行记录 ID。npusim 的报告流程可以使用这些数据库。

这里的 tick 是模型记录时间的单位。我们先直接比较 tick，避免把界面将小数纳秒显示成“0 ns”的舍入现象混进来。本文把 popped 到完成之间称为“原始区间”；**这个区间可能包含排队或其他阻塞，不能未经确认就叫作纯同步等待耗时**。

## 现象一：原始记录有一段较长区间，数据库却只保留了 1 tick

### 实际看到什么

在 MegaMoE 的 chip0、core0、第一个 Vector 子核上，我们选出这一条指令：

- 名称：`WAIT_FLAG`；原始指令编号：`55005`。
- 原始指令地址：`0x4010550c`。
- 参数：`PIPE:MTE3, TRIGGER PIPE:VEC, FLAG ID:0, #V:0,`。
- 对应数据库执行记录 ID：`61022895396573`。

同一条指令在两处保存的时间如下：

| 数据来源 | 开始 tick | 结束 tick | 两者相差 |
| --- | ---: | ---: | ---: |
| 原始二进制中的 popped / 完成记录 | 31577 | 45986 | 14409 tick |
| helper 数据库中的执行记录 | 45985 | 45986 | 1 tick |

结束时间是一致的，差别在开始时间。也就是说，**如果直接用这条数据库记录画一个长条，画出来只能是最后 1 tick，无法从这个长条读回原始的 14409 tick 区间**。换成 Perfetto 或 Insight 都不会凭空恢复数据库里没有保存的起点。

这不是一个孤立例子：MegaMoE 每卡有 376 条 WAIT_FLAG，原始记录中 319 条的区间大于 0；数据库中的 376 条则全部为 1 tick。统计见 audit.json（配套归档文件）。

### helper 的“零时长处理”具体做了什么

开发人员提到 helper 有零时长处理逻辑后，我们检查了本机库内的 SQL 字符串，以及实际运行日志。找到的逻辑可以用下面这句话描述：

> 对指定类别的同步记录，如果开始时间和结束时间相等，就把开始时间往前移 1 tick，让这条记录具有一个非零的展示宽度。

其中包括 SET_FLAG、WAIT_FLAG 等。对应更新的核心是 `ExecInstrTickStart = ExecInstrTickStart - 1`，条件包含 `ExecInstrTickEnd = ExecInstrTickStart`。MegaMoE 每卡日志记录 `normalized zero-duration sync instructions: 792`；792 是该逻辑处理的全部指定同步记录数量，不是 WAIT_FLAG 的数量。SQL 字符串保存在 normalization_sql_strings.txt（配套归档文件）。

**这条 SQL 只解释“0 tick 如何变成 1 tick”，并不直接解释“原始的较长区间为什么先变成了 0 tick”。** 后者涉及 helper 如何接收、解释和组织同步事件，需要按具体实现确认。此前简单说“helper 把 WAIT 归一成 1 tick”，容易把这两个步骤混为一谈。

另一个值得注意的事实是，这条 WAIT 数据库记录带有 `ExecInstrIsDurationExcluded=1`，扩展参数也标有 `is_duration_excluded=1`。这提示它可能被有意当成同步位置标记，并排除在某些时长统计之外；仅凭字段不能确定全部设计意图，但不能忽略它就把现象定性为 bug。

### 对使用者有什么影响，需要开发者回答什么

如果这些记录本来就只用于标出“同步发生在哪里”，1 tick 的宽度可能完全符合预期。如果使用者把这个宽度理解为等待区间，就会得到误导性的结果。我们想确认的是：

1. 当前版本的 WAIT_FLAG 数据库记录，设计上是**同步位置标记**，还是应当表达某种**等待区间**？`ExecInstrIsDurationExcluded` 的具体语义是什么？
2. 如果需要分析等待或阻塞，官方应读取哪份数据、使用什么命令？是否应该保留原始 popped 起点，还是需要按另一套规则计算？
3. 有没有原生的采集/导出选项能完成这件事，避免我们自己还原文本？

默认采用原始二进制还原文本，再交给原生 msprof 生成 Insight 报告。msprof 自己也会按规则裁剪部分 WAIT 区间，所以我们没有把原始区间直接宣称为最终应显示的等待时间。这个办法是用于核对的替代路径，不是对 helper 设计的否定。

## 现象二：数据库已有同一执行记录 ID，后续 INSERT 被拒绝

### “重复 ID”在这里是什么意思

`ExecutedInstructions` 表要求每条执行记录的 `ExecInstrId` 唯一。helper 写入一条记录时，如果表里已经有相同 ID，SQLite 会拒绝这次 INSERT，并报 `UNIQUE constraint failed`。

这里说的不是“程序循环执行同一个源码地址不合法”，也不是 Dispatch 输入中的 expert ID 重复。源码地址可以重复执行，输入 expert ID 也属于另一个问题；这里冲突的是 **helper 给数据库执行记录分配的 ID**。

### 一个可以直接定位的例子

MegaMoE chip0 的 helper 日志中有下面这条错误：

```text
insert instr failed rc=19 err=UNIQUE constraint failed: ExecutedInstructions.ExecInstrId
exec_id=57999238379230 instr_id=14046 core=0 sub_core=2
```

它对应 core0 的第二个 Vector 子核中的一条 `RV_SMOV`。原始事件和最终数据库记录如下：

| 数据来源 | 开始 tick | 结束 tick | 两者相差 |
| --- | ---: | ---: | ---: |
| 原始二进制中的一对记录 | 15357 | 15358 | 1 tick |
| 最终数据库内同一执行记录 ID 的行 | 15354 | 15354 | 0 tick |

该原始记录的指令编号是 `14046`，指令地址是 `0x4010b008`。数据库中保存的地址为 `0x10b008`，相差 Vector 镜像的装载基址 `0x40000000`；不能因为地址显示不同，就直接把它们当作两条无关的源码指令。完整比对见 duplicate_audit.json（配套归档文件） 中 chip0.db 的第一条 details。

我们能够确认三件事：同一个执行记录 ID 的 INSERT 被拒绝过；最终数据库仍保存着 15354→15354 这一行；原始文件里可以找到 15357→15358 的完整记录对。

一种待验证的解释是：helper 先记录了指令的某个提前阶段，随后处理实际执行阶段时又使用了同一 ID，却走了 INSERT，而没有按协议更新已有行。**这是根据最终记录和错误日志提出的解释，不是已经定位到 helper 源码分支的结论。** 现有错误行也没有直接打印“被拒绝行准备写入的起止时间”，所以不能把这一点说得比证据更确定。

### 为什么不能简单清库或者忽略报错

本轮仿真每次都使用新运行目录和新数据库，这些错误在一次运行内部就会出现。旧数据库中的历史数据不是这个复现的前提。

关闭唯一约束或忽略 INSERT 也不能直接解决时间问题：前者可能留下多条含义不清的记录，后者可能继续保留较早的 0 tick 行。究竟应该更新旧行、区分不同阶段，还是使用不同 ID，取决于模型事件和 helper 的配对规则。

最终两例的规模如下：

| 用例 | 每卡在日志中被拒绝、且最终 DB 中已有行的 ID 数 | 其中 raw 恰好只有一对完整起止 | 其余情况 |
| --- | ---: | ---: | --- |
| MegaMoE | 433 | 401 | 32 个涉及多阶段事件，未猜测性修正 |
| Dispatch | 1156 | 1156 | 这些 ID 均能找到唯一完整起止对 |

这些数字不能直接解读成“丢了 433 或 1156 条算子指令”。有些 ID 已有数据库行，只是最终保留的时间区间可能与原始记录不同。数据库结构检查 quick_check 为 ok，也只证明文件结构可读，不能证明时间信息符合预期。

### 希望开发者帮助确认

1. 对示例 `exec_id=57999238379230`，15354 的记录和 15357→15358 的记录分别是什么阶段？是否应该共用一条数据库执行记录？
2. 如果应该共用，后来的信息是否应更新原记录？如果不应该共用，ID 应如何区分？
3. 当前 helper/model 是否是匹配版本？有没有已知修复、配置开关或官方配对规则可以直接使用？

这次 helper 库的 SHA256 是 `954c36d053b00f3aeca21c1505db4821ac5b8094c2c3b5a9148da033dd7637b3`，方便先确认讨论的是同一个二进制版本。

## 两件事之间的关系

第一件事讨论**同步记录应当表达什么时间语义**；第二件事讨论**同一个执行记录 ID 再次写入时应如何处理**。本文第二个例子是普通的 RV_SMOV，不在上面那条同步归一化 SQL 的指定类别中。

因此，知道 helper 有“零时长处理”，还不足以解释或解决重复 INSERT；反过来，修复 INSERT 冲突，也不能自动决定 WAIT 应该显示哪个区间。我们希望分别确认这两件事，并优先采用原生工具支持的用法。


原始证据文件路径指向配套归档或云盘 developer_discussion 目录，不包含在技能本身；使用具体ID前确认是同一采集版本。
