我们在 CANN 9.3.0-weekly.20261104.01 上运行了 E1 真实依赖模型（GMM1→真实 ACTQ→GMM2，不执行 Dispatch/Combine/Unpermute），以及独立官方 GMM1、GMM2。E1 只模拟原 rank0，逻辑 EP8；目标 PR9589，32 AIC + 64 AIV。官方 GMM1/GMM2 均由独立 torch_npu.npu_grouped_matmul 自然选型，不是我方 pureGMM。修复我方加载适配后，三项模型均正常结束（退出码 0、TASK_DONE），各自约定的完整数值输出均与 Golden 逐位一致。本轮请求是 callback→helper 记录语义及正确导出方式，无需修复已通过的数值结果：原 helper 已完成写盘，但我们的严格 native 检查拒绝将这些记录认定为完整指令生命周期。

请协助确认同一模型版本中 RV_SEND 的 start/end 究竟对应整条 ISA 指令，还是内部微操作/阶段；现有字段如何正确区分、配对和绘图。我们已备好小体量真实回调样本、模型反汇编片段、helper 日志及版本身份，可先离线判断；无需先重跑耗时数小时的模型。现阶段证据不足以认定模型计算错误或模型 bug。

1. 问题发生在哪一层

ELF/输入装载 → 模型执行 → 指令 start/end 通知 → 原 helper 的 map/数据库 → 我方 reader/严格检查 → 图
   已修复       已完成       已无损旁路留存           已写盘              完整 native 被拒绝

ELF 是模型实际执行的编译产物；callback（回调）是模型向外报告的一条通知。helper 是接收通知并写入数据库的程序。native 在本文中指有完整性与生命周期依据的原生指令记录；模型退出成功、数值通过和完整 native 验收是三件分别检查的事。

实际异常来自我方严格检查抛出的 ValueError：

Native helper has incomplete/dropped instruction records

这会使原完整流水工作流失败，不能当成无影响的 warning；但这句笼统错误也不能反推模型原始通知已经丢失。 原 helper 的写盘失败计数为 0、状态正常，只能说明它把自己保留的记录写出，不能证明记录语义完整。旁路 tee 按实际注册关系转发每条通知并另存原件，已核对接收/转发、ACK、封帧、文件哈希与独立终态计数；这些证明已观察通知得到保留，仍不证明模型每条 ISA 指令都发出了可配对通知。

2. “覆盖”和“未配对”具体指什么

下面三行都是示意，非实测数据。S/E 分别表示 start/end，key 是 helper 内部用来归档通知的键。

覆盖：map[key]=S@10；随后 map[key]=S@12 → 后者替换前者；不是算子张量被覆盖。
未配对：只见 E@20 → 可能是合法的完成通知；没有 S 就不能补一个起点算耗时。
多解：同一身份见 S@10、S@11、E@20、E@21 → 两种配对都成立；不能凭“最近”猜。

helper 的 overwrite 计数属于内部 map 行为，既不等于旁路原件丢失，也不自动等于两次独立指令执行。仅有 end 也不一律是坏数据：已对绑定模型证明 BAR、GET_BUF、RLS_BUF、DSB 的特定路径只发完成通知；它们可画完成瞬点，无法恢复进入/等待区间。

RV_SEND 的困难是通知身份不足。 已核对的 ST 路径把同一个 ISA 对象分发到不同内部单元；gather/scatter 单元的结束通知可以投影到相同的指令身份。现有回调没有可证明的 unit/stage 身份；某些字段是 PC，而非微操作编号。额外 start 的来源也未全部闭合。传输顺序、临时指针或“start/end 数量接近”都不能补回这些信息，因此不能把某个 end 擅自标成整条 RV_SEND 完成。

4. 同版 CANN 以前确实跑通过吗

确实通过过。 Unpermute 的 r02/r03 历史回执记录了 native DB→JSON 成功、84 个上下文和数值 exact；SDK 版本与本次一致，helper SHA 也一致。

但旧模型二进制 SHA 未保存或未找到，不能说“与本次同一模型二进制”。旧链路也没有本次新增的 callback 守恒和 RV_SEND 分类检查。我们保留旧成功结论，同时不把它扩展成“同版 SDK 的所有算子、所有通知类别都能按当前严格规则导出完整流水”。

建议先看复现包中的真实小 frame、对应 ISA/模型反汇编片段、helper 日志和身份清单。真实 RV_SEND 小样本（core5/type2/id116659、core9/type1/id128532）在现有 CPU classify() 中可直接复现 UNKNOWN_MISSING_ENDPOINT；这仅复现原样本的配对判定，不加载 helper/model，也不认证整流。包内 CPU_REPLAY.json 则是构造输入调用真实 helper，用于验证 map 覆盖机制；两类证据的输入与证明范围不同。包内按三档使用材料：小证据离线核对 → 有限 CPU 解析复现 → 必要时以原 ELF 和原输入重新执行模型。各档的确切命令、依赖、输出和预期拒绝结果见复现入口；本次交接不启动模型、不重读完整 raw/大流水。

包内入口：证据索引 · 三档复现 · 冻结工具说明。原始大数据与旧冻结包保持原样；优先发送小证据，不要求开发者先接收数十 GB 原件。
