npusim 流水记录异常：部分指令的开始、结束通知无法配对

在 CANN 9.3.0-weekly.20261104.01 的 npusim 仿真中，模型能够正常结束，输出数值正确，helper 也生成了数据库。但读取流水记录时，发现部分指令只有开始或结束通知，以及同一标识下存在多条开始、结束通知，无法确定对应关系，因而无法生成完整的指令时间线。

本报告以官方 GroupedMatmul GMM2 为主要复现用例，附上实际配置、ELF、输入及异常记录。烦请协助定位该记录异常；若这些通知属于预期行为，也请提供相应的解析方式。

2. 实际现象

模型结束并写出数据库后，我们的流水解析检查报错：

ValueError: Native helper has incomplete/dropped instruction records

这条错误来自我们的解析检查，不是 npusim 的计算报错。错误文字本身也不能证明模型丢失了通知。当前可直接观察到的现象如下。

现象一：同一标识下的开始、结束数量不一致。 官方 GMM2 的一组实际 RV_SEND 记录如下，时间保留原始 tick：

core=5，rawtype=2，PC=0x401052cc，ID=116659，编码=0xc0000017

RVECLD：START 13000
RVECST：START 13221、13222、13222；END 13231、13231

上述 RVECLD 记录只有一条 START；RVECST 有三条 START、两条 END。现有记录无法让我们唯一确定各条开始与结束的对应关系。core=9、ID=128532 也出现相同形态。完整字段和原始字节见 evidence/rv-send-continuation/RV_SEND_EXACT_SAMPLES.json。

现象二：helper 的记录存在覆盖。 对 helper 的 CPU 复核显示，相同 key 再次写入时可以替换先前的开始记录；重复结束通知也会增加 overwrites 计数。这里的“覆盖”指流水记录，不是算子输出张量。对应结果见 evidence/helper/CPU_REPLAY.json，它使用构造输入验证 helper 行为，与上面的真实模型样本分开保存。

此外，官方 GMM1 中每个 AIC 的四条 BAR 记录只有 END。若这类记录本来只表示完成通知，需要按此含义解析，不能按缺失 START 推算等待时长。

3. 预期行为与影响

希望采集结果能够保留各条通知，并支持按明确的规则生成时间线：表示执行区间的记录可以确定起止对应关系；只表示某个时刻的通知可以明确识别，不被误当成缺失端点。

目前计算结果不受影响，但部分指令区间无法还原，完整流水解析因此中止。我们尚不能确定问题应在模型通知、helper 保存方式还是解析规则中修正。

4. 复现步骤

  1. 解压附件，进入 sim-developer-handoff 目录。
  2. 先按 REPRODUCTION.md 的“小样本复核”运行 CPU 命令，即可读取以上真实记录并复现当前解析器的 UNKNOWN_MISSING_ENDPOINT 判定。此步骤不运行模型。
  3. 如需重新产生模型通知，使用同一版本 CANN、模型和 helper，展开 reproductions/G2-reproduce.tar.gz，按同一文档中的原始运行命令及路径准备要求运行官方 GMM2。
  4. 模型结束后检查 helper 数据库及对应通知，重点查看上述 PC/ID 的 START、END 记录，并保留运行日志。

附件包含原配置中的绝对路径，因此完整模型复现需要匹配环境并准备相应目录，不能直接在任意解压路径运行。完整 SDK 和大体积原始回调流未随包提供；小样本、原 ELF、输入、配置及日志已包含。
